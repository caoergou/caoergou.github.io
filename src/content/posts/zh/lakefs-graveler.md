2008 年，中本聪在比特币白皮书里用了两段话解释 Merkle Tree——轻描淡写，却奠定了整个「内容寻址」思想在工程领域的地位。十几年后，一家叫 lakeFS 的公司把同一套逻辑用到了数据湖版本控制上，造出了一个叫 Graveler 的存储引擎。

这两件事表面上风马牛不相及。一个管钱，一个管文件。但拆开来看，它们解决的是同一个问题：**在一个不可信的、分布式的世界里，如何保证「这份数据，就是你以为的那份数据」？**

---

## 区块链的核心发明：哈希即身份

先把区块链拆成最小单元。

一个比特币区块本质上是三件东西的组合：一批交易记录、前一个区块的哈希、以及这批交易记录本身的哈希摘要（Merkle Root）。

哈希的关键性质是**内容决定身份**。把「Alice 转给 Bob 1 BTC」这条记录改成「Alice 转给 Bob 0.001 BTC」，哈希值就会面目全非。这意味着：

> 只要你能拿到区块的哈希值，就能验证区块里每一笔交易是否被人动过手脚——不需要看全部数据，只需要沿着 Merkle Tree 往上验证一条路径就够了。

Merkle Tree 的结构很简单：把所有交易两两哈希、再把结果两两哈希，一路向上，最终汇成一个 Merkle Root。一个区块里有一万笔交易，想验证其中某一笔是否存在，只需要 log₂(10000) ≈ 14 次哈希计算。

这是**把「数据完整性」从 O(N) 降到 O(log N) 的核心魔法**。

区块之间用哈希串联：每个区块里都包含前一个区块的哈希。改了 1000 块之前的一笔交易？这个区块的哈希就变了，导致下一个区块的「prevHash」失效，导致再下一个也失效……整条链从那里开始全部断掉。这就是「不可篡改性」的来源——不是魔法，是级联失效。

## Git 的方案为什么不够用

lakeFS 的诞生动机是：**给数据湖提供 Git 式的版本控制**。分支、提交、合并、回滚——这些 Git 工作流对代码很好用，对数据为什么不行？

问题出在规模和存储介质上。

Git 是为本地文件系统设计的。它每次提交一个目录，把目录树存成「Tree Object」——每个目录对应一个 Tree Object，里面列出子目录和文件的哈希。一个文件改了，它所在的目录 Tree Object 要重写，父目录也要重写，一直到根。这在本地磁盘上没问题，写一个文件和写一百个文件的成本差距不大。

但数据湖放在对象存储上（S3、GCS、Azure Blob），**每写一个新对象，代价相当于写 4 MiB 数据的网络开销**。更关键的是：数据工程师的仓库可能有十亿个文件，哪怕每天只改 5% 的数据，那也是 5000 万个文件。Git 的目录树模型在这种规模下直接爆炸。

另一个问题是 diff 效率。两个相邻提交的差异只有 1000 个文件，但如果要扫描整棵目录树才能找出差异，代价就是 O(总文件数) 而不是 O(差异大小)。这在十亿文件规模下是不可接受的。

## Graveler：把哈希逻辑带进对象存储

lakeFS 的解法叫 **Graveler**——一套为对象存储量身定制的内容寻址键值存储。

先看最基本的数据单元，`ValueRecord`：

```
ValueRecord {
  key:      文件路径（如 "data/2025/01/part-000.parquet"）
  identity: 文件内容的哈希（如 sha256）
  value:    文件在对象存储上的实际地址 + 元数据
}
```

这里有一个精妙的设计：`identity` 和 `value` 是分开的。`identity` 是内容摘要，`value` 是存储地址。Graveler 判断两条记录是否「相同」，看的是 key + identity，不看 value——这让比较操作极其廉价，不需要拉数据内容。

一个 Graveler 文件（即一个 Range 文件）的 ID 计算方式如下：

```
valueRecordID = h( h(key) || h(identity) )
fileID        = h( valueRecordID_1 || valueRecordID_2 || ... || valueRecordID_N )
```

注意这个结构——**Range 文件的 ID 由它包含的所有记录共同决定**。改了其中任意一条记录，整个文件的 ID 就变了。和区块链的 Merkle Root 如出一辙。

## 两层 Merkle 树：扁平即高效

单个 Range 文件一般是 1–10 MB，包含一段连续键空间（按文件路径排序）里的所有 ValueRecord。

但一个仓库有十亿文件，不可能都塞进一个 Range。lakeFS 把所有 Range 文件再往上汇一层，叫 **Meta Range**。

结构如下：

```
Meta Range
├── Range_A（键空间 aaa... ~ eee...）
├── Range_B（键空间 eee... ~ kkk...）
├── Range_C（键空间 kkk... ~ ppp...）
└── Range_D（键空间 ppp... ~ zzz...）
```

Meta Range 里存的是每个 Range 的「最大键」和「Range 文件 ID（哈希）」。一个 commit 就是一个 Meta Range 的哈希指针。

这是一棵**高度为 2 的 Merkle 树**，结构上等价于 B+ 树：Meta Range 是根节点，Range 文件是叶节点，每层都是内容寻址的。

对比区块链：
- 区块链的 Merkle Root 汇聚的是「这个区块里的所有交易」
- lakeFS 的 Meta Range 哈希汇聚的是「这个 commit 里的所有文件元数据」

验证逻辑完全一致：给我一个 commit 的 Meta Range 哈希，我就能沿树向下验证任意一个文件的状态——而且是 O(log N) 的代价。

---

## 写入放大的奇迹：99% 复用率

这是 Graveler 最有意思的地方。

假设某次提交只修改了 `data/2025/10/` 目录下的 500 个文件，这些文件的路径全部落在 Range_C 的键空间里。Graveler 的写入过程是这样的：

1. 重写 Range_C，生成新的 Range_C'（哈希变了）
2. Range_A、Range_B、Range_D **一个字节都不用动**，直接复用原来的文件
3. 重写 Meta Range，把 Range_C 的条目换成 Range_C'，生成新的 Meta Range'

**整个提交操作只写了 2 个新文件**（Range_C' 和 Meta Range'），其余所有数据都通过哈希引用复用。

根据 lakeFS 在真实设计伙伴数据集上的测量，一个仓库每天的变化率在 5–20% 之间。以每天 20 次提交来算，单次提交平均改动不到整个仓库的 1%，对应的 Range 复用率 **>= 99%**。

这就是为什么区块链思想能用在数据湖上——但又不能直接用区块链：区块链每个区块自成一体，交易不跨区块复用；Graveler 的 Range 文件跨 commit 共享，这是它在空间效率上的关键差异。

---

## 可变的归可变，不可变的归不可变

Graveler 负责的是**已提交数据（committed metadata）**，它是不可变的——文件一旦写入，永远不变，只靠哈希引用，没有原地修改的概念。这和区块链的「不可篡改性」完全同源。

但系统里还有另一类数据：**分支指针和暂存（staged）修改**。

分支本质上是指向某个 commit 的指针。每次提交或合并，分支指针都要更新——这是高频的随机写操作，和「不可变」的设计理念格格不入。

lakeFS 的解法是双轨制：
- **不可变数据**（已提交的 Meta Range / Range 文件）→ 直接存对象存储（S3 等），天然高可用
- **可变数据**（分支指针、暂存元数据）→ 单独维护在 KV Store（PostgreSQL、DynamoDB）里，用 CAS（Compare-and-Set）乐观锁保证写入一致性

这个分层和区块链的设计也暗合：区块链的历史区块（已确认）是不可变的，而「内存池（mempool）」里的待确认交易是高度可变的，两者用完全不同的存储和访问策略。

## 一次思想的传承

回头看，内容寻址这个思想的传播路径很有意思：

**Ralph Merkle（1979）** 提出 Merkle Tree，证明可以用 O(log N) 的代价验证任意元素是否属于一个集合。

**中本聪（2008）** 把它用在比特币交易验证上，再加上区块间的哈希链，造出了「分布式账本」。

**Git（2005 年，比比特币还早）** 把内容寻址用在了代码版本控制上：每个 commit、tree、blob 都是哈希寻址的对象，是同一套思想的另一个独立实现。

**lakeFS Graveler（2021）** 则是把 Git 的思路推进到对象存储规模：保留内容寻址和 Merkle 树的核心，但重新设计了树的结构（两层 B+Tree）和分裂策略（基于哈希的随机分裂），让 Range 文件能在海量 commit 之间高效复用。

每一代传承都不是简单的照搬，而是在理解底层数学之后，根据新的约束（规模、网络延迟、写入代价）做出新的工程取舍。

这或许也是技术演化的基本模式：好的思想不会消亡，只会在新的土壤里重新生长。
